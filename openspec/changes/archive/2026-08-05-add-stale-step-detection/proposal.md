## Why

讀者打開一份幾天前產出的導讀時,面板只說「行號可能漂移」——整份一個警告,等於整份一起可疑。讀者無從判斷哪一步還能信,只能逐步自己對照原始碼,或乾脆放棄這份導讀。更糟的是 snippet 預覽:它照著 JSON 裡的行號從現行檔案切幾行貼出來,程式碼漂移後貼出的是一段**完全不相干、但外觀完全正常**的程式碼,配著原本的說明文字。跳轉錯位讀者至少看得出來,這種靜默的錯誤內容看不出來。

CodeWalk 的目標場景是持續維護中的專案,主幹每天在動,導讀寫完沒幾天就會進入這個狀態。本變更讓面板能精準指出「哪一步已經不可信」,並在導讀整體失準時引導作者重新產生——**強化而非推翻**既有的衍生快照紀律(`decisions.md`:導讀不維護、過期即刪):我們讓過期變得看得見、讓重生變得沒有摩擦,而不是去修補一份已經過期的導讀。

## What Changes

- **`.codewalk.json` 新增可選的「錨」欄位**:產出當下把每個 step 與 `kind: 'snippet'` 項目所引用的程式碼**原文**一併存入。`kind: 'diff'` 不錨——它自帶 `diffText`,且描述的舊碼本來就注定不存在。
- **載入時逐 step 驗證錨**:比對錨與現行檔案內容。相符即準確;不符則在整份檔案內搜尋該段原文——找到**唯一一處**視為單純位移,直接採用新行號;找不到、或找到多處,判定該步**失準**。
- **失準的 step 改變呈現**:顯示錨定的**原文**(明確標示為產出當時的內容、現行版本已不同),不再貼出現行檔案的內容;並提供「開啟現行檔案」動作——只開檔、不選取任何行,不假裝知道新位置。
- **新增整份層級的重生引導**:導讀出現失準步驟時,面板顯示提示與「複製重生指令」按鈕。指令內容來自 `.codewalk.json` 新增的可選欄位,由**產生器自述如何重生自己**;extension 只負責顯示與複製,**不執行任何產生行為**(MVP 邊界)。
- **既有的整份 `refDrifted` 警告降為退路**:導讀含錨時改以逐步狀態呈現;不含錨的導讀維持現行行為完全不變。
- **非破壞性**:schema 只新增可選欄位,不改名、不刪除。舊導讀在新版 extension 下行為不變。
- **產生器需配合**(不在本變更的程式碼範圍,但屬同一批交付):`.claude/skills/explain-change/` 及 harness 母本兩處都要改為寫入新欄位。合約定案後才動,由 `shared/schema.ts` 與本變更的 spec 作為依據。

### Out of Scope / Non-goals

- **用 `git diff` 比對 ref 與 HEAD 來自動校正行號**——明確否決,不留後路。git 能追行號、追不了語意;校正成功省下讀者幾秒,失敗卻要承擔改名/刪除/重寫/淺 clone/commit 不在本地的全部路徑,且會產出「行號正確、敘述錯誤」的假可信,比現況更危險。
- **單步重生、per-step `ref`、混合 `ref` 的導讀**——會破壞 `ref` 作為「這份導讀對應哪個 commit」的對外語意,並使 walk-player 既有「作答紀錄以 `ref` 判定過期」的行為失效。
- **在 extension 內實際執行產生**——二期範圍,出場條件見 `decisions.md`。
- **多份導讀的組合與拼接**——後續構想,獨立成案。
- **導讀分享時的程式碼脫敏或遮蔽機制**——同一 repo 內錨定原文不造成任何額外暴露(git 無檔案層級權限),且 `diffText` 已存在同類內容;風險僅在人為單獨分享導讀時成立,本階段不設計機制。

## Capabilities

### New Capabilities

- `stale-step-detection`:以產出當下存下的程式碼原文(錨)驗證導讀各步是否仍與現行程式碼相符,涵蓋錨的驗證與搜尋定位、單純位移時的行號跟隨、失準步驟的判定與呈現,以及導讀整體失準時的重生引導。

### Modified Capabilities

- `walk-player`:「ref 漂移偵測」requirement 需改寫——導讀含錨時,漂移訊號由整份單一警告改為逐步狀態;不含錨時維持現行行為。連帶影響 snippet 預覽與檔案跳轉在失準步驟上的行為。

## Impact

**協定與格式(對外合約)**

- `shared/schema.ts`:新增錨欄位與重生指令欄位及其驗證;`.codewalk.json` 是對外開放格式,欄位形狀一經發布即為合約
- `shared/protocol.ts`:`walkLoaded` / `stepChanged` 需攜帶逐步的失準狀態,現行的單一 `refDrifted` 布林不足以表達

**Extension host**

- `src/refDrift.ts`:目前僅有 `getWorkspaceHead()` 與字串比對的 `isRefDrifted()`,需擴充或新增模組承載錨驗證
- `src/snippetPreview.ts`:失準時改送錨定原文而非現行檔案內容
- `src/fileJump.ts` / `src/viewProvider.ts`:失準步驟的「只開檔不選取」跳轉行為

**Webview**

- `ui/render.ts`:逐步失準標記、原文區塊與其標籤、重生引導與複製按鈕。視覺樣式須與 `pitfall` 等內容型提示區隔(沿用既有的系統層級警告樣式慣例)

**外部相依**

- `.claude/skills/explain-change/`(本 repo)與 harness 母本兩處產生器
- `docs/glossary.md`:新增「錨」「失準」「位移跟隨」,並與既有的「漂移」明確區分

**效能**(已實測,不需再評估)

- 全份驗證 21 步 / 40 個錨 / 23 個相異檔案:內容全部命中 0.37 ms,最壞情況(全部落入搜尋路徑)0.70 ms。載入時全份驗證、不快取。
- 錨定原文使該份導讀 JSON 由 50.5 KB 增至約 76 KB(+50%),對照 `decisions.md` 已記錄的載入實測不構成問題。

## Open Questions

以下 5 點於需求訪談中刻意留白,需在 design/specs 階段定案:

1. **錨欄位的精確形狀與命名**——直接掛在 step 與 snippet 物件上,還是集中為獨立區塊?牽動 design 的取捨,提前定會綁死。
2. **重生引導的觸發門檻**——任一步失準即顯示,還是需達到一定比例?傾向前者(門檻是憑空發明的規則),但尚未實際走讀過失準的導讀,不敢定。
3. **單純位移(唯一匹配)成功時,是否要對讀者標示行號已移動**——內容逐字相同、理論上無欺騙,傾向不標示;屬 UI 決策,需看面板實際擁擠程度。
4. **`walk-player` spec「ref 漂移偵測」requirement 的改寫幅度**——修改既有 requirement 或新增一條?兩者對既有 scenario 的影響範圍不同。
5. **重生指令欄位的格式約定**——純文字單行、允許多行、是否限長?
