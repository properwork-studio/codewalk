# 後續功能評估

> **狀態:探索中,不是承諾。** 這份文件記錄評估過的方向與判斷依據,任何一項要動工都得先走 OpenSpec change 流程。
>
> 建立於 2026-08-07,第一批 marketplace 上架準備完成後回頭討論。

## 摘要

| 方向 | 工作量 | 價值 | 是否動到格式合約 | 建議 |
|---|---|---|---|---|
| 程式碼上的導讀標記 | 小 | 高 | 否 | **先做這個** |
| 讀者註記 | 小~中 | 待驗證 | 否(但存放位置要決定) | 跟上一項合併設計 |
| 錄製 | 中 | 高 | **很可能要** | 先寫 design 確認格式,實作看投入意願 |
| PR Review | — | — | 否 | 拆解後多半不需要新功能 |

---

## 1. 程式碼上的導讀標記

### 是什麼

在編輯器的 gutter 上標示「這幾行有導讀講過」,點擊可以跳進對應的那一步。CodeTour 有同類功能,叫 Tour Markers。

### 為什麼排第一

目前 CodeWalk 只有一個方向:**打開導讀 → 跳到程式碼**。

加了標記之後多一個反向入口:**讀 code 時發現這段有人講過 → 點進導讀**。後者才是日常更常發生的情境——你在追一段不懂的邏輯,忽然看到旁邊有現成的解說。

而且它幾乎是免費搭在既有機制上:`anchor` 讓標記在程式碼改動後仍然定位準確,失準的就不畫。這是 stale-step-detection 已經解決的問題,直接復用。

### 技術路徑

- `vscode.window.createTextEditorDecorationType()` 建 gutter icon 的 decoration type
- 掃 `.codewalk/` 建立 `file → [{walkPath, stepIndex, lineRange}]` 的索引
- 監聽 `onDidChangeVisibleTextEditors`,對可見的編輯器套用 decoration
- 位置用 `buildAnchorReport()` 的結果修正(`shifted` 跟隨新行號,`stale` 不畫)

### 待決議題

- 一份檔案被多個導讀引用時,gutter 只有一格空間——顯示數量?還是只標示「有」然後點擊時給選單?
- 索引什麼時候重建?每次開檔掃一次會太頻繁,但檔案監看又是額外的複雜度
- 導讀很多時 gutter 會不會太吵?需不需要開關

## 2. 讀者註記

### 是什麼

讀者在導讀的某一步留下自己的疑問或理解,像 Kindle 畫線那樣。

### 技術上很簡單

存 `workspaceState` 就好,repo 裡已經有兩個同構的現成範例:`ProgressStore` 和 `AttemptStore`。照抄結構,連 `ref` 失效判斷的模式都一樣。

### 真正要想清楚的是產品問題

**這些註記給誰看?**

- **只給自己** — 價值取決於導讀會不會被反覆讀。如果導讀主要用在一次性上手,讀完就不再回去,註記幾乎不會被翻出來
- **要能分享** — 那就得寫成檔案、要處理多人同時編輯的衝突、要決定註記算不算導讀的一部分。這是另一個量級的工程

建議先做「只給自己」的版本觀察使用情況,不要一開始就設計分享機制。

### 跟第 1 項合併設計的理由

兩者底層是同一件事:**讀者在程式碼與導讀之間留下的痕跡**。

如果註記也能在 gutter 上顯示標記(「我在這行留過筆記」),那它跟「這行有導讀講過」可以共用同一套 decoration 機制與索引結構。分開做會寫兩次;一起設計只寫一次,而且行為一致。

## 3. 錄製

### 是什麼

在 VS Code 裡直接建立導讀:選一段程式碼、寫敘述、存成一個 step。

### 真正的價值

不是省打字,是**自動填 `anchor` 和行號**。

手寫 `.codewalk.json` 時這兩個欄位最容易出錯,而且錯了要到播放時才發現。錄製時它們是白送的——選了哪幾行,`startLine` / `endLine` / `anchor` 就自動是那幾行。

### 它會改變產品的性質

目前 extension 對檔案系統是唯讀的。錄製之後就變成編輯器:

- 要處理編輯中的暫存狀態
- 要有「草稿 / 已存」的概念
- 要處理寫檔失敗
- webview 要多一套編輯模式的狀態機

### 最大的風險是範圍失控

證據在 CodeTour 的 README:光「Recording Tours」一節就有 15 個子節——Step Titles、Text Selection、Re-arranging、Deleting、Editing、Linking Tours、Primary Tours、Conditional Tours⋯⋯

錄製功能一旦開始做,需求會自己長出來。

**要做的話建議硬性限縮成三個動作:加一步、刪一步、調順序。** 其他一律不做,等有人真的抱怨再說。

### 跟 CLAUDE.md 的關係

`CLAUDE.md` 寫著「MVP 期禁止把產生邏輯寫進 extension」。

**錄製不等於產生**——產生是 AI 讀 diff 自動寫(shell out `claude -p`),錄製是人手動建立,不涉及 AI。技術上不牴觸那條規則。

但那條規則的精神是「保持播放器單純」,做錄製等於放寬它。這需要在 `openspec/decisions.md` 明確重新定案,不是默默做掉。

## 4. PR Review

這個詞涵蓋三種不同的東西,拆開之後多半不需要新功能:

### a. 針對 PR / diff 產生導讀

**已經存在。** harness 的 `explain-change` skill 就在做這件事,產出的正是 `.codewalk.json`。

這屬於產生器範疇,不是播放器的事。

### b. 在面板裡留 comment、approve

**不建議。** 要串 GitHub API、處理 OAuth、同步 comment 狀態,而且要跟 GitHub 官方的 PR extension 正面競爭。

投入產出比在這個階段完全不成立。

### c. 導讀附在 PR 上,讓 reviewer 照著走

**現在就能做,不需要任何新功能。**

作者把 `.codewalk.json` commit 進 PR 分支,reviewer checkout 之後用 CodeWalk 走一遍。這是流程問題,不是功能問題。

真要降低摩擦的話,可以做一個小功能:偵測到目前分支有導讀就主動提示。但那是小功能,不是「PR Review 模式」。

**行動項:把 (c) 的用法寫進 README 或使用文件即可。**

## 附錄:格式合約的時機問題

這是這份文件裡最需要現在就決定的事。

**如果最終要做錄製,`.codewalk.json` 的格式很可能得動。** 錄製會冒出播放時不需要的欄位:草稿狀態、編輯時間、產生器 metadata、步驟的暫時 id⋯⋯

而格式是明文定義的對外合約(見 `CLAUDE.md` 與 `shared/schema.ts`),改它等同破壞性變更——別人 repo 裡放著的舊 JSON 會壞掉。

**現在使用者數是 0,改格式沒有成本。** 等到有人寫了產生器、有人 repo 裡放了幾十份導讀,再改就很痛。

### 建議

即使暫時不實作錄製,也值得先把錄製的 design 寫出來,只為了回答一個問題:

> 格式需不需要改?需要的話,趁現在改。

這件事的成本是幾小時的設計思考,能省下的是未來一次破壞性變更。

---

## 建議順序

1. **程式碼上的導讀標記 + 讀者註記**——合併設計,共用 decoration 與索引機制,不動格式
2. **錄製的 design**(不實作)——只為確認格式要不要改,要改就趁現在
3. **錄製的實作**——看投入意願,範圍嚴格限縮在加/刪/排序
4. **PR Review**——不做功能,把 (c) 的用法寫進文件
